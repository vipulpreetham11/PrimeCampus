# M1 — Setup & People: module report

Branch: `module/m1-setup-people` · Date: 17 Oct 2026 · Brief: `docs/modules/M1.md`

## Summary

M1 adds the school's master data and people screens on top of M0:

- **School setup** (`src/features/setup/`): school profile (version-checked), academic years + make current, classes,
  sections per year, subjects, class subjects, bell schedules (editor + two presets + overlap checks + "effective
  from"), attendance mode (with upcoming changes), and a calendar (Students / Staff / staff group; month grid on
  desktop, list on phones; weekly pattern and date-range editors).
- **Staff** (`src/features/staff/`): staff groups (salary only with `staff_finance.*`), directory, create/edit via
  `get_staff`, a separate confidential finance card (own query key, `gcTime: 0`), and teaching assignments by staff
  and by section.
- **Users & logins** (`src/features/users/`): list, create login (Edge `provision`, one operation id per dialog),
  add a role to an existing login (`find_school_account` → `grant_membership`), admissions duty, disable a role,
  reset password, disable/enable login (Edge `set_status`), and link/unlink logins on staff, guardian and student
  records.
- **Students & guardians** (`src/features/students/`): keyset-paged directory with filters, profile with placement
  history, guardians and linked login, version-checked edit, a sensitive-identifiers card, guardian search/create/edit,
  and placement moves (preview → commit with one operation id).
- **Admissions** (`src/features/admissions/`): keyset-paged enquiries list, follow-ups due, enquiry detail with
  timeline, follow-up form, and admit (from an enquiry or blank, one operation id per form).

All five required commands pass. There are **190 unit/component tests** (13 files) after the review fixes. The
live Playwright suite (M0's 6 tests + M1's 12) passed **twice in a row, 18/18**, against the live project, in the
Demo School only. After the review fixes it was run once more: 18/18 (see "Review fixes"). No backend files were
changed. M2 was not started.

## Bugs found and fixed during live testing

1. **New login did not appear in the users list** (commit `dc23f15`). `provisionLogin` / `resetLoginPassword` are
   plain async calls on purpose, so the temporary password never enters the TanStack cache. Because of that, nothing
   invalidated the users list. Fix: `useRefreshAfterLoginChange()` invalidates users, staff list/record, student,
   guardian and guardian-search after provision or reset.
2. Test-only issues (not app bugs): a substring match on "Current" also matched the "Make current" button. A toast
   assertion used the server's wording, but the client shows its fixed safe CONFLICT message.

## Review fixes

Done after the owner's review (17–18 Oct). Each item lists where it is verified. All five commands pass
(13 files / 190 tests). The live suite was run once afterwards: **18/18** (M0 6 + M1 12).

1. **CONFLICT retry loop.** The class, section, year, subject and staff-group dialogs now keep only the row id and
   read the row from the latest query data. Each dialog is keyed on the row's version, so after CONFLICT + refetch
   it reopens on the current version. Before this, it kept resending the old version and failed every time.
   Test: `m1-review.test.tsx` › "subjects: CONFLICT → reload → the reopened form saves with the NEW version".
2. **Provision id lifetime.** The create-login dialog stays mounted while closed. Its typed values and operation
   id survive closing and reopening, so a retry resumes the same `provision` operation. Test: "network failure →
   close → reopen → retry resends the same id and username".
3. **Operation-id reset rule.** A new shared `OperationTracker` (`src/lib/operation.ts`) is used by create login,
   admit and placement moves:
   - The id is renewed only after success or a definite refusal (`VALIDATION_ERROR`, `FORBIDDEN`, `DUPLICATE`,
     `NOT_FOUND`, `CONFLICT`, `LIMIT_REACHED`).
   - It is kept after `UNKNOWN` / `NETWORK` / `TEMPORARILY_UNAVAILABLE`.
   - Editing the form after a kept id produces a new id, because the payload changed.
   - Placement moves: `DUPLICATE` ("operation id already used for different content") renews the id and
     requires a new preview.

   Tests: "OperationTracker — …" (10 cases), "a definite refusal (DUPLICATE) starts a new id", and the placement
   DUPLICATE test.
4. **SQLSTATE mapping.**
   - Kept: 23505 → `DUPLICATE`; 23P01 / 23514 → `VALIDATION_ERROR` (fixed messages).
   - 23502, 23503, 22P02, 22001, 22007, 22008 → `UNKNOWN`: "Something went wrong" + request id.
   - Malformed ids from the URL (`/students/abc`, `/staff/…`, `/admissions/…`, `?lead=`) are rejected by
     `routeId()` before any request and shown as "That record was not found."

   Tests: `errors.test.ts`.
5. **Staff group salary.** An existing default can't be emptied. The form says "To change it, enter a new amount."
   and sends nothing. Test: "an existing default cannot be emptied".
6. **Staff-group weekly pattern.** Only the weekdays changed for that group are saved. Each row is labelled
   "School default" / "Set for this group" / "Changed". The school default itself still saves the whole week.
   Test: "a group change to Saturday sends just Saturday".
7. **Class subjects.** Mappings to retired subjects are shown read-only ("Retired") and sent unchanged in the
   full-replace save. Test: "shows the retired subject read-only and includes it unchanged".
8. **Upcoming teaching assignments.** Both lists show current and upcoming assignments; an upcoming one shows
   "Starts <date>". The request no longer filters on "active today". The section page's class teacher is still
   today's. Test: "section page lists an assignment starting later".
9. **Salary not in the shared cache.** `useStaffGroups` (directory filter, staff form, calendars) strips
   `default_monthly_salary_paise` before caching. The staff-groups screen reads salary through its own key
   `staff-groups-finance` (`gcTime: 0`), and only with `staff_finance.read`. Test: "the shared staff-groups cache
   never holds the salary".
10. **E2E password hygiene.**
    - Passwords are only ever checked as booleans in `expect()`. Assertions target the dialog's close button,
      never the secret element.
    - `trace` / `screenshot` / `video` are off in `m0.spec.ts` and `m1.spec.ts`.
    - The failure page snapshot ("error context") is disabled with `PLAYWRIGHT_NO_COPY_PROMPT=1` in the config.

## PRD / brief / DB mismatches

The database wins in each case. Items 1–3 were confirmed by the owner: "follow the SQL; the brief is wrong there".

1. **Bell slot kinds.** The brief says "period / break / assembly etc."; the SQL accepts only `period` and `break`.
   The editor offers just those two.
2. **Weekly patterns cannot be holidays.** Holidays are date ranges only. The pattern editor offers working / half day /
   weekly off.
3. **Student half days need a bell schedule** (SQL check). Both editors require one and say so.
4. **Raw constraint errors from invoker RPCs.** Several `security invoker` RPCs (e.g. a duplicate section/subject
   code, overlapping teaching assignments, a second class teacher) raise plain Postgres errors (23505, 23P01, 23514…)
   with no `hint`. Under CLAUDE.md rule 3 these would show as "Something went wrong". The client maps only the
   user-fixable ones: 23505 → `DUPLICATE`, 23P01 / 23514 → `VALIDATION_ERROR`, each with a **fixed** safe message
   (never the SQL text). All other raw SQLSTATEs stay "Something went wrong" + request id (review fix 4).
   `tests/unit/errors.test.ts` covers it. Suggestion for the owner: raise hinted errors in SQL instead.
5. Gaps found during planning, resolved by the owner in migration `20261005001900_m1_backend_gaps.sql` and the updated
   Edge function, and used as instructed:
   - `get_school_profile` (version + `can_edit`)
   - section capacity / sort order / year in the snapshot
   - `get_guardian` plus guardian versions
   - `set_status` for an Admin who manages every school of the login
   - `get_staff`
   - `staff.member` in `get_context`
   - `attendance_modes` in the snapshot
   - `list_leads` keyset `(created_at, id)`
   - login + `can.link_login` on the student profile
6. **Disable your own role:** the brief says the server blocks it and to show its message. The UI hides the Actions
   menu on your own card, so that server message is not reachable from the UI. Not exercised.
7. **Parent role needs a separate guardian link.** `grant_membership` adds the Parent role only. The children appear
   after `link_account(guardian)`. The Add-role dialog says so, and E2E test 5 does both steps.
