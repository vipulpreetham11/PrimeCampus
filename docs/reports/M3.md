## Summary

- **Fee setup** (`src/features/fees/setup/`): fee heads (kind fixed after creation; DUPLICATE code shown under
  Code), receiving accounts (cash desk / bank / UPI; an edit sends only changed keys, an emptied field is sent as
  `""` to clear it), terms (with `invoices_issued`, the returned note, Retire), the **price list** grid (classes ×
  heads for one term, saved per class; an empty cell is **"No price"**, visibly different from ₹0), concession
  presets (fixed ₹ or % in basis points), the year's late-fee rule (save / replace / retire), optional fees (head +
  section roster, only changed rows, one operation id per Save). Read-only for `fees.read`.
- **Concessions**: grant from the statement or the Concessions page (student picker), for the whole year or one
  term; after a grant, "Already-issued invoices aren't changed: INV/… — add an adjustment if needed" with a link to
  each invoice on the statement. Revoke with a reason.
- **Invoices**: preview a term (whole school or one section) → per student: lines, gross, concession, net, and
  **Will be issued / Already issued / Will be skipped + the reason** (the server's order of checks) → Issue with
  one operation id → issued / already existing / **skipped students with names and reasons**. Apply late fees
  (added / invoices with a pending cheque). Link to the opening-balances import.
- **Collect payment** (`/fees/collect`, `fees.manage`): find student → open invoices oldest due first → method
  (cash / UPI / bank transfer / cheque), amount, account, reference → allocation **oldest-first by default, editable
  per invoice, capped at each invoice's balance (for a cheque: minus what other pending cheques plan), Save only
  when the rows add up exactly**. Over the dues: blocked, with "Collect only the dues (₹X)" and "Record the extra as
  a payment exception". Cheques are recorded as pending ("does not reduce the dues").
- **Receipts**: printed from the receipt snapshot only (school, receipt no, date, student, class, method, account,
  reference, payer, allocations, total, **amount in words, Indian numbering**, collector, issue time), reversals
  listed under it, A5 (default) / A4 print CSS that prints only the receipt.
- **Statement** (staff and parent): invoices with Unpaid / Partly paid / Paid / Cancelled and Overdue in words,
  lines, concessions, adjustments; payments with **where each went**; reversals; pending cheques (with planned
  allocations) and bounced cheques; total due; open exceptions. Staff actions: add adjustment (discount / extra
  charge), waive late fee, cancel invoice, reverse a collection, grant/revoke concession, add opening balance.
- **Corrections**: cheques register (clear with planned or changed allocations, bounce, cancel with version);
  payment exceptions (record unidentified money, resolve with version).
- **Reports**: day book (filters: dates, method, account, collector, search; **server totals for the filters**;
  Load more; CSV of every page), collection report, dues (year always sent; class / section / term / overdue /
  with balance; "Class not set"; totals row = sum of rows; CSV; stacked rows on phones).
- **Parent / student** (`/child/fees`, `child.view`): the selected child's statement and receipts, read-only; the
  child comes from the context, never the URL.
- **Opening-balances import**: the M1b wizard gained the `opening_balances` dataset (needs `fees.manage` to commit;
  preselected from Fees → Invoices); the job page shows `amount_totals` — "Ready to import ₹…" and "Imported so far
  ₹…".
- **Navigation**: "Fees" for `fees.read`, "Fees" under the child pages for `child.view`; the fee tabs are
  capability-driven (Collect payment / Invoices only with `fees.manage`). `/fees` opens Collect payment for
  `fees.manage`, otherwise Dues. M3 removed from every "coming" list.

## Brief ↔ database mismatches (no backend changes made)

1. **`issue_opening_balance` has no operation id**; replays are keyed by admission no + head code + reference
   (same amount → `replayed`, same invoice; different amount → DUPLICATE with the invoice number, shown).
   ~~Its `p_due_date` had no default~~ — **resolved by 2320**; the UI now leaves it out when empty.
2. **`cancel_invoice` takes an operation id but does not store it** (safe to repeat by state). `waive_late_fee`,
   `clear_cheque`, `bounce_cheque`, `revoke_concession`, `resolve_payment_exception`, `evaluate_late_fees` take no
   operation id (safe by state); `clear_cheque` / `bounce_cheque` take no expected version.
3. **`post_collection` CONFLICT = the same operation id is still in flight**, not someone else's edit (CLAUDE.md
   rule 3 says "reload"). Handled as "Not confirmed", keeping the id (owner-confirmed).
4. ~~**Statement has no student name/class**; the Owner can't list students~~ — **resolved by 2320**
   (`statement.student`). The Owner still can't search students (no `students.read_all`): the student picker says
   so and points to Dues / Day book, whose rows link to the statement.
5. ~~**Collection report has no filters, so day-book totals can't follow the filters**~~ — **resolved by 2320**
   (`list_collections.totals`). Still: `get_collection_report.by_collector` / `by_account` carry labels only (no
   ids), and the RPCs offer no list of collectors — the day book's "Collected by" choices come from the rows loaded.
   Reversals in the collection report are counted by the date of the reversal, collections by the received date
   (labelled).
6. **`evaluate_late_fees.skipped_pending_cheque` lists every invoice with a pending cheque**, not only those that
   would have been charged; shown as "Invoices with a pending cheque (not charged): N".
7. ~~**No planned allocations of pending cheques on the statement**~~ — **resolved by 2320**; the cheque form caps
   each invoice at balance − other pending cheques and the statement shows "Planned for".
8. **The same UPI/bank reference is DUPLICATE only on the same receiving account**; another account accepts it.
9. **`list_optional_fee_roster`'s wrapper defaults the section to null but the RPC requires it**; the UI always asks.
10. **`get_dues_report` with no year mixes every year's balances with the current year's class**; the UI always
    sends a year (owner-confirmed).
11. **`reverse_collection` replay returns only `reversal_id`**; "still reversible" is recomputed from the statement.
12. **A regular head priced for some classes of a term but empty for another class skips that class's students**

## Design notes

- **One money action = one operation id** (`src/features/fees/money-action.ts` over `OperationTracker`): same id for
  the same payload after NETWORK / UNKNOWN / TEMPORARILY_UNAVAILABLE (and, for `post_collection`, CONFLICT — a new
  `keep` option of `OperationTracker.failed`); renewed after success or a definite refusal. An uncertain failure
  freezes the payload and locks the form ("Not confirmed — check the statement before trying again"); the only ways
  on are "Try again (same …)" or "Discard" after a second confirmation. Never retried automatically.
- **Unknown is never ₹0**: amounts render only from a loaded query inside `DataState`; `MoneyText` shows "—" for
  missing; "Paid" only from the server's `payment_state`; pending cheques "not counted as paid"; dues "No issued
  invoices" instead of ₹0; price "No price" vs ₹0.00.
- **Money**: `parseRupees` (string math, never negative, 0 only where allowed) and `formatPaise` in `src/lib/money.ts`;
  percent → basis points by string math; CSV amounts as rupees with 2 decimals; CSV text cells that look like
  formulas are prefixed with `'`.
- **After any money mutation** the statement, dues, day book, cheques, report, exceptions, concessions, receipt and
  preview queries are invalidated.
- **Dashboards are not in this brief**: the Accountant placeholder now says the fee screens are live under Fees and
  points its at-a-glance dashboard (PRD §16) to M4 — an assumption, change if wrong.

### 1. Possible duplicate payment

- `post_collection` DUPLICATE with `details.possible_duplicate` → "₹X by cash for Aarav Sharma was already
  recorded at 20 Oct 2026, 1:26 am (receipt RCT/…). Is this a second, separate payment?" with **Open that receipt**
  (the receipt id comes from the student's statement; the statement link if it isn't there yet) and **Yes, record
  another payment**, which re-sends the same form with `p_allow_possible_duplicate: true` and a **new** operation id
  (DUPLICATE is a definite refusal). The reference DUPLICATE (UPI / bank, no flag) keeps its own message ("Already
  posted on receipt …").
- Unit: `m3-pages` › "a possible duplicate … asks; 'Yes' re-sends with the flag and a new id"; the reference test
  now also asserts the question is **not** shown. Live: `m3-review` R5 (a second identical cash payment → the
  question; the link opens the first receipt; Yes → a second receipt; the two requests: no flag / flag, different
  ids).
- **Observation (server order):** the possible-duplicate check runs before the reference check, so re-typing an
  _identical_ UPI/bank payment (same amount, same UTR) gets the question first; the reference DUPLICATE is met when
  the amount differs, or after "Yes". `m3.spec` step 4 now re-sends the same UTR with a different amount.
- The live specs give their payment amounts a per-run paise offset, so two runs within 30 minutes don't look like
  one payment typed twice.
